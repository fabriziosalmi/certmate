Enable Deploy Hooks

Run shell commands, and deliver to deploy targets, after certificate issuance or renewal

Commands run as the CertMate process user. Only admins can manage hooks.

Available Environment Variables

CERTMATE_DOMAIN, CERTMATE_CERT_PATH, CERTMATE_KEY_PATH, CERTMATE_FULLCHAIN_PATH, CERTMATE_CHAIN_PATH, CERTMATE_EVENT, CERTMATE_DRY_RUN (only set during Test runs)

Blocked Shell Patterns

For safety, the command field rejects command substitution, chained commands, and redirects to absolute paths: &&, ||, ;, $(...), ${...}, `...`, > /, <<, eval, source. A simple pipe (|) and a redirect to a relative path are allowed. The command runs inside the CertMate container, which carries sh, bash, curl and openssl — not ssh, scp or systemctl. References to CertMate's own secrets (.env, settings.json, the API bearer token, client secrets, vault tokens) are also blocked; certificate and key files are not, because installing them is what a hook is for. If you need any of those, put the logic in a script file inside the container and call the script path directly (e.g. /opt/scripts/deploy.sh).

These hooks run for every domain after certificate issuance or renewal.

A target hands the certificate to a service after issuance or renewal. A webhook target sends it to an HTTPS endpoint you name, and sends the private key too only if you put a key variable in the payload and confirm the destination. Each confirmation is in the audit log. The threat model and every field are in docs/deploy-hooks.md.
