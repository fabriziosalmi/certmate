Quick Start

  1. The setup page creates the first admin and turns sign-in on with it, so the instance is never left open. Add more people, each a Viewer, an Operator or an Admin, in Settings → Users.
  2. After the first sign-in a short wizard asks for the contact email your certificate authority uses and how names are validated: DNS-01 through your DNS provider, or HTTP-01 over port 80. If you closed it, the same choices are in Settings → DNS and Settings → CA.
  3. On Certificates, click New, enter the domain and click Create Certificate.
  4. For scripts and CI, create a key in Settings → API Keys and send it as a Bearer token (see API).

Renewal runs every night between 02:00 and 03:00 UTC and renews each certificate when it is due: 30 days before expiry with the default threshold, or, when the threshold is more than half of the certificate's lifetime, a third of the lifetime (half of it under 10 days). No cron setup needed.

Validation and DNS Providers

The CA checks that you control each name before it issues. A certificate picks one of two ways under Challenge Type, and Settings → DNS sets the default:

  • DNS-01: CertMate places a TXT record through your DNS provider. Wildcards work. It needs a credential that can create and delete TXT records on the zone.
  • HTTP-01: the CA fetches a file from http://<name>/.well-known/acme-challenge/, so port 80 of each name must reach CertMate, directly or through your reverse proxy. No DNS credentials, and no wildcards.

Certificate Authorities

Add accounts in Settings → CA with Add CA Account; each authority has a default account. A certificate can pick another CA and account when it is created.

  • Let's Encrypt: free DV certificates, 90 days, no EAB. Rate limit: 50 certificates per registered domain per week. For tests, use Let's Encrypt (Staging).
  • Actalis: free DV certificates, 90 days, a European (Italian) CA. Requires EAB: generate the credentials in your Actalis customer area under Manage with ACME. The free plan is single-domain only (no wildcard, no SAN).
  • DigiCert ACME: paid DV/OV/EV. Requires External Account Binding (EAB key and HMAC) from your DigiCert account portal.
  • Private CA: any ACME-compliant internal CA, such as step-ca. Provide its ACME directory URL (https) and, if it enforces one, an EAB credential.

The list also has ZeroSSL, Google Trust Services, Sectigo and SSL.com.

Check configuration in the CA account dialog checks that the fields a CA needs are filled in before you save. For a Private CA it also fetches the directory URL. It does not register an account or test EAB credentials with the CA.

API

Create a key in Settings → API Keys and send it as a Bearer token. Each key has a role (Viewer reads, Operator also creates and renews, Admin also changes settings), an optional expiry and an optional list of the domains it may touch. The token is shown once, when the key is created. 

Authorization: Bearer YOUR_TOKEN

Settings → General also has an API Bearer Token field: that token has full admin access on every certificate, so give scripts and agents a scoped key from API Keys instead.

Common endpoints

  • GET /api/certificates
  • POST /api/certificates/create
  • POST /api/certificates/{domain}/renew
  • GET /api/certificates/{domain}/download (ZIP bundle)
  • GET /api/certificates/{domain}/download/{cert|chain|fullchain|privkey|combined} (privkey, combined: operator+)
  • GET /api/activity
  • GET /api/deploy/history

curl examples

# Create a certificate (an Operator or Admin key)
curl -X POST http://localhost:8000/api/certificates/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"domain":"example.com"}'

# Download full bundle as ZIP
curl -H "Authorization: Bearer $TOKEN" \
  -o example.com.zip \
  http://localhost:8000/api/certificates/example.com/download

Full reference: Swagger (interactive try-it-out) or ReDoc (read-only).

Multi-account DNS

Useful when you manage zones under different cloud accounts (for example one Cloudflare tenant per customer, or separate Route 53 accounts for production and staging).

  1. In Settings → DNS, click Add Account on the provider. Name it (for example production) and paste the credentials.
  2. Tick Set as default account on one of them: it is used when a certificate does not pick one.
  3. When creating a certificate, an account list appears for a provider with more than one account.
  4. From the API, pass account_id alongside dns_provider.

Client Certificates

A client certificate identifies a person, a device or a service to a server that asks for one: API mTLS, VPN access, user login. CertMate signs them with a CA of its own, separate from the authorities in Settings → CA.

  • On Certificates, switch the view to Client and click New. Single Certificate takes a Common Name, a Usage Type and a validity of 1 to 3650 days. Bulk Upload (CSV) takes a file with the columns common_name, email, organization and, optionally, cert_usage and notes.
  • With Generate private key (recommended) ticked, CertMate makes the key. Untick it and paste a certificate signing request instead: the key stays on the device that made it.
  • Open a certificate to download it as .crt, .key, .csr or .pfx. The .pfx is encrypted with the Windows .pfx Export Password in Settings → General, and is refused until one is set.
  • Each row has Revoke and Renew. A nightly run renews a certificate 30 days before it expires, or at a third of its validity when that is shorter.

A server that checks these certificates needs CertMate's client CA, and its revocation list to refuse the revoked ones. Both are served without signing in:

  • GET /api/client-certs/ca (the CA certificate, PEM)
  • GET /api/crl/download/pem (the revocation list, PEM)
  • GET /api/ocsp/status/{serial} (one certificate's status as JSON, serial in decimal)

ACME Server

CertMate can answer ACME (RFC 8555) itself, from a root of its own, so that certbot, lego, acme.sh and cert-manager on your network get certificates for internal names. It is off until you turn it on.

  1. In Settings → ACME, tick Serve ACME and click Save. While it is off, every /acme/ address answers 404.
  2. Clients connect over HTTPS only. If TLS ends at a reverse proxy, set BEHIND_PROXY so CertMate sees the original scheme; Also over plain HTTP is for a lab.
  3. Require an EAB key is on by default. Under New EAB key, give the names and networks a key may order (*.lab.internal, 10.20.0.0/16) and click Create. The HMAC key is shown once, with the command for each client.
  4. Give clients the directory URL the tab shows, which ends in /acme/directory. The hosts that use the certificates must trust the ACME root: download it from the same tab.

What it issued is on Certificates, in the ACME view. Its certificates are valid 45 days by default (1 to 365, in the same tab).

  • GET /acme/directory (where clients start)
  • GET /acme/root (the root to trust)

Inventory

Inventory lists the server certificates CertMate knows of: the ones it holds (Managed) and the ones it found elsewhere (Discovered). Client certificates are not in it.

  • Managed is read from this instance's disk.
  • Discovery configuration (admins) turns on what finds the rest: probing endpoints (host or host:port), watching Certificate Transparency logs through crt.sh for your domains, domain registration expiry, and domain health checks (SPF, DMARC, MX, blocklists, response headers, old TLS versions). Each runs once a day; Scan now runs the endpoint sweep and the CT-log poll at once.
  • Adopt (operators) issues a new certificate from CertMate for a discovered certificate's names and takes over its renewal. Forget removes the row; the certificate itself is not touched.
  • A certificate is superseded when every endpoint it was seen on now serves another one, or when CertMate renewed it. Superseded certificates are hidden until you tick Show superseded.

Crypto Readiness Report

The Cryptographic readiness band on Inventory classifies every certificate in the inventory by key and signature algorithm, to plan the move to post-quantum algorithms. Client certificates are not in it. It is a report only: issuance does not change.

  • Weak: RSA under 2048 bits, an elliptic curve below P-256, DSA, or an MD5 or SHA-1 signature. Replace these first.
  • Acceptable: RSA from 2048 bits, ECDSA from P-256. Strong today, but quantum-vulnerable: NIST IR 8547 deprecates RSA and ECDSA after 2030 and disallows them after 2035.
  • Modern: Ed25519 and Ed448. Also quantum-vulnerable, on the same NIST dates.

Report opens a printable page with Print / Save as PDF; CSV and JSON download the same data.

  • GET /api/inventory/crypto-report (JSON; ?format=csv for CSV)

Backup & Restore

  • What's in a backup: the settings and every certificate, in one archive. Credentials and private keys are in it only when CERTMATE_BACKUP_PASSPHRASE is set, and the archive is then encrypted with it. Without it, a backup is a snapshot of the configuration and the certificates that cannot restore the instance on its own.
  • Automatic: before each settings change, and before a restore.
  • Manual: Settings → Backup, Create Unified Backup. Download it from Existing Backups to keep a copy off this host.
  • Restore: the Restore backup button on a backup in the list; a backup that cannot restore says why. An archive kept elsewhere comes in first through Restore From Elsewhere, Upload Backup.
  • Retention: at most 50 backups, and none older than 30 days.

Troubleshooting

DNS provider authentication failed
The token may be wrong, expired or scoped too narrowly. Check in your provider's console that it can create and delete TXT records on the zone. Settings → DNS has no connection test: try the first certificate against Let's Encrypt (Staging), whose rate limits are separate from production's.
Certificate creation hangs or times out
Usually slow DNS propagation. Most providers settle within a minute or two, some take up to 10. If one provider is reliably slow, select it in Settings → DNS and raise its Propagation wait for that provider (stored as dns_propagation_seconds).
Let's Encrypt rate limit hit
50 certificates per registered domain per week. The CA's error is in Activity. For tests, select the Let's Encrypt (Staging) Certificate Authority: its limits are higher and separate, and browsers do not trust its certificates, which is the point.
Deployment status says "Unknown" or "Not Verifiable"
CertMate connects to the certificate's own name (port 443 unless set otherwise) and compares the certificate served with the one it holds. A wildcard cannot be checked until it has a probe host, a name it covers: set one in Settings → Probe. To check every certificate at once, use Check all deployments (the broadcast icon) on Certificates.
UI looks broken / Alpine.js failed to load
A red banner at the top of the page says so. CertMate serves Alpine.js itself, as /static/js/alpine.min.js, so something between the browser and CertMate blocked that file: a proxy, a content filter or a browser extension. Try a hard refresh (Cmd+Shift+R / Ctrl+F5) and check the browser console for the blocked URL.

Liveness: /health returns JSON with scheduler, disk, and cert directory checks, useful as an external probe.

Report an issue

When something goes wrong, including the items below makes the fix faster: most reports stall on missing context, not on hard root causes.

  • CertMate version (footer of every page, or /health)
  • How CertMate is running (Docker tag / Kubernetes / bare gunicorn) and host OS
  • Steps to reproduce, with the domain or operation involved if relevant
  • What you expected vs. what happened
  • Browser console errors (F12 → Console) for UI issues
  • Container or gunicorn logs around the failure timestamp (redact tokens before pasting)
  • /health JSON output
  • Screenshots help, especially for layout glitches
