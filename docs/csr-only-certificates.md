# CSR-only certificates

Closes [#599](https://github.com/fabriziosalmi/certmate/issues/599).

Some appliances — load balancers, HSM-backed devices, network security boxes —
generate their private key on the device and cannot export it. They can hand out
a Certificate Signing Request and nothing else.

CertMate can issue and renew for those. You submit the CSR; CertMate obtains the
certificate from the configured CA and manages the certificate and chain. **The
private key never leaves the device, and CertMate never stores one.**

---

## The workflow

1. Generate the key and the CSR **on the device**.
2. Submit the CSR to CertMate through the API (below).
3. CertMate runs the ACME challenge and obtains the certificate.
4. CertMate stores `cert.pem`, `chain.pem`, `fullchain.pem` and the CSR itself —
   and no `privkey.pem`.
5. At renewal, CertMate re-submits the **stored CSR** to the CA.
6. If the device rotates its key, submit the new CSR to the **reissue**
   endpoint — see [Key rotation](#key-rotation).

## Issuing

Pass the PEM CSR as `csr` on the ordinary create endpoint:

```bash
curl -X POST https://certmate.local/api/certificates/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d "$(jq -n --arg csr "$(cat device.csr)" \
        '{domain: "api.example.com", dns_provider: "cloudflare", csr: $csr}')"
```

`domain` must be one of the names inside the CSR — it is what the certificate
directory is named for, and what renewal, the health check and deploy hooks find
it by. A CSR that does not cover it is refused rather than filed under a name it
does not serve.

**What must be omitted**, because a CSR already decides it:

| Field | Why |
| --- | --- |
| `san_domains` | The certificate covers the names inside the CSR. A CSR is signed over its own subject and SANs, so a request naming different ones would get a certificate different from what it asked for, with nothing to say why. |
| `key_type`, `key_size`, `elliptic_curve` | The key was generated by the device. CertMate does not choose it and will not pretend to. |

Both are refused with a 400 rather than ignored.

The `csr` value is limited to 64 KiB (65,536 bytes); a larger one is refused
with a 400 before it is parsed.

## What a CSR-only certificate looks like

```json
{
  "domain": "api.example.com",
  "exists": true,
  "days_left": 74,
  "needs_renewal": false,
  "private_key_state": "external",
  "private_key_present": false,
  "usable": null
}
```

`private_key_state` has five values, and the distinction between two of them is
the point:

| State | Meaning |
| --- | --- |
| `present` | A matching key is beside the certificate. |
| `missing` | There is no key and there should be. **Forces `needs_renewal`** — this is what a restored share-safe backup produces, and it used to report itself healthy ([#608](https://github.com/fabriziosalmi/certmate/issues/608)). |
| `mismatched` | A key is there but does not match the certificate. |
| `unknown` | Nobody looked — the storage-backend listing path fetches the certificate without the key on purpose. |
| `external` | **CSR-only.** There is no key here and there should not be. Does **not** force `needs_renewal`. |

`usable` is `null` for `external` rather than `false`: the certificate *is*
usable, on the device that holds the key. CertMate cannot answer for a key it
does not have.

Without that distinction a CSR-only certificate would be reissued on every
renewal sweep, burning CA rate limit for a file that must not exist.

## Renewal

`certbot renew` will never renew these, and that is not a CertMate limitation —
certbot says so itself when it issues one:

> Certificates created using --csr will not be renewed automatically by Certbot.
> You will need to renew the certificate before it expires, by running the same
> Certbot command again.

So that is what CertMate does: the scheduled renewal re-runs issuance with the
stored `csr.pem`, using the CA, DNS provider, account and alias recorded in the
certificate's metadata. Nothing about the schedule changes — a CSR-only
certificate is renewed by the same sweep, at the same threshold, as every other.

Two consequences worth knowing:

* **If `csr.pem` goes missing**, renewal fails loudly rather than silently doing
  nothing. Submit the CSR again from the device that holds the key.
* **If the CA returns the same certificate** — what a repeat request inside a
  CA's reuse window produces — the renewal comes back with `renewed: false`
  and the message "Reissued from the stored CSR, but the CA returned the same
  certificate", rather than advancing `renewed_at` past an expiry that stood
  still.
* **`force` has no effect.** A CSR renewal always re-submits the stored CSR,
  whether or not `force` is set.

## Key rotation

Submit the new CSR to **reissue**, with the same `domain`:

```bash
curl -X POST https://certmate.local/api/certificates/device.example.com/reissue \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d "$(jq -n --arg csr "$(cat device-new.csr)" '{csr: $csr}')"
```

The stored CSR and the `csr_fingerprint` in metadata are replaced, and
subsequent renewals use the new one. The old certificate keeps being served
until the CA answers, so there is no window without one.

Not `create`: that refuses a domain which already has a certificate, with
`409 CERTIFICATE_ALREADY_EXISTS`. This page used to say "the same way", which
read as create and left delete-then-create as the only path — a gap with no
certificate at all, on the feature you are using precisely because the key
matters (#876).

The same rules as on create apply: the certificate covers the names inside the
CSR, so `san_domains` and the key options must be omitted. SANs the current
certificate has are **replaced** by the CSR's names rather than added to
them.

## Deploy hooks

A CSR-only certificate has no key to deploy, so:

* **Shell hooks** run normally, and `CERTMATE_KEY_PATH` is **not set** — rather
  than set to a path that does not exist, so a hook doing
  `cp "$CERTMATE_KEY_PATH" …` fails visibly instead of silently copying nothing.
  `CERTMATE_CERT_PATH`, `CERTMATE_CHAIN_PATH` and `CERTMATE_FULLCHAIN_PATH` are
  set as usual.
* **Typed deploy targets** (the Kubernetes secret target) cannot serve one: they
  all publish the key alongside the certificate. They report exactly that,
  naming the reason, instead of a generic "certificate files unreadable" on
  every renewal. The check is on the files, not the metadata: any certificate
  with a `fullchain.pem` and no `privkey.pem` gets this report.

Use a shell hook that fetches only the certificate and chain.

## What is refused, and why

| Situation | Result |
| --- | --- |
| The CSR does not cover `domain` | Refused with a 422. The directory is named for `domain` and everything later finds it by that name. |
| The CSR's signature does not verify | Refused with a 400, before anything is written. The CA would reject it anyway, after CertMate had created a directory and reported progress. |
| The CSR names no domains (no CN, no SAN) | Refused with a 400. |
| `domain` already has a CertMate-managed private key | Refused: a 409 `CERTIFICATE_ALREADY_EXISTS` when its `cert.pem` is there (the usual case), otherwise a 422. Converting it would leave the old `privkey.pem` beside a certificate it cannot serve — an unusable pair, reported as `mismatched` from then on. Delete the certificate first if you mean to move its key onto a device. |
| A CSR covering a name outside the API key's `allowed_domains` | Refused with a 403, per name, the same way SANs are. |

The status codes are those of a synchronous create. With `async`, the 400 and
403 cases are still answered immediately; the 409 and 422 cases are checked
during issuance and fail the job instead.
