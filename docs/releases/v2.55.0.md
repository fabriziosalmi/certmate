## v2.55.0 (two certificates for one domain)

One feature, built in steps, and two fixes.

- **A certificate can be named apart from its domain, so one domain can hold two** (#854, #1367, #1368, #1369). A second certificate for `example.com`, from another CA such as a private one, gets a name of its own, `internal.example.com`: **Name** in the create form's Advanced Options, `name` on `POST /api/certificates/create`, `--name` in the CLI, `name=` in the SDK and `name` in the MCP server's create tool. It is issued for `example.com`, its host, and every later action (renew, reissue, download, deploy, delete) takes the name. A name has the shape of a DNS name, is not a wildcard unless it is the wildcard certificate's own domain, and an IP certificate takes none. Verified on Let's Encrypt staging: two certificates for one host, the one named apart issued, renewed and reissued for the host, and deleting it left the other as it was. See [Create a certificate](../api.md#create-a-certificate).
- **Every answer says where a certificate is served** (#1360, #1364, #1365, #1366). Certificate answers carry `host`: the address of an IP certificate, the host of a certificate named apart, and its name otherwise. Deploy hooks get `CERTMATE_HOST` beside `CERTMATE_DOMAIN`, webhook targets `{{host}}`, and every event about a server certificate `host`. The deployment check, discovery, CT-log monitoring, domain health and domain registration look at the host. The SDK, the CLI and the MCP server read it.
- **A key restricted to domains is judged on a certificate's name too** (#1363, #1367, #1370). A certificate is a key's when its scope covers its name and every name it covers: its host, its SANs and the DNS names in it. The dashboard's batch download, the cache statistics and the metrics read only the names covered, so a key scoped to a host was given a certificate named outside its scope; they judge the name now, as every route on a certificate did. A certificate is issued for its host, and a CSR must cover it.
- **Fix: an IP certificate is looked for at its address** (#1359). The deployment check probed a host called `ip-203-0-113-5`, the dashboard's browser check fetched it, and discovery probed it. They use the address now; the browser check also follows a `deployment_host`, which it ignored. CT-log monitoring and domain health leave an IP certificate out.
- **Fix: discovery calls a served certificate issued only when CertMate holds it** (#1358). A sweep decided from the host alone, so a certificate from another CA, still served after a renewal that was never deployed, read as one CertMate issued. Its fingerprint decides now: `issued`, `imported` or `probed`.
- **Docs:** the README and the ACME server page say what the server certifies, and when a CA run apart fits better (#1361); the webhook target section shows the body it sends (#1357).

**Backups.** An archive that holds a certificate named apart from its domain must not be restored into an older version: an older version ignores `host`, so it would ask the CA for the name on the next reissue, and check the name instead of the host. See [After a downgrade](../backup.md#after-a-downgrade).

Under the hood: the real-certificate release gate gains a test of two certificates for one host on Let's Encrypt staging. certmate-sdk and certmate-cli, which take `name` and read `host` in this repository, are published to PyPI on their own.

The API contract moves to **2.61** (MINOR): **2.59** adds `host` to every certificate answer, the create answer and a create job's result; **2.60** adds `host` to every event about a server certificate, `CERTMATE_HOST` to deploy hooks and `{{host}}` to webhook targets; **2.61** lets `POST /api/certificates/create` take `name`.
