## v2.32.2 (What CertMate says about a certificate's key, and about whether it has expired)

A patch release: two fixes, both in what the API and the dashboard report about
a certificate that is already there. Neither changes how certificates are
issued or renewed.

Both were reported by the same operator, three times over six months, in #786.

### A certificate with no private key was reported as healthy

v2.29.0 shipped the fix for "a certificate with no private key is reported as
healthy, and the scheduler leaves it alone". It landed on the wrong path.

`get_certificate_info` inspects the private key only when the instance has no
storage backend configured. Every instance has one: the container always builds
a `StorageManager`, and `StorageManager` defaults to the local filesystem. So
that inspection never ran on a real installation, and the branch that did run
decided the key state from whether the backend's answer happened to contain a
key. The default backend read `privkey.pem` off the disk and dropped it before
answering, so the answer never contained one.

The visible symptom is the one reported: `private_key_present` and `usable`
come back empty, and `private_key_state` is `unknown`, for every certificate.
The consequence is larger. `needs_renewal` raises an alarm only when the key is
`missing` or `mismatched`, and on that path it could be neither, so:

```
$ rm certificates/example.com/privkey.pem
$ curl -s .../api/certificates/example.com | jq '{private_key_state, needs_renewal}'
{ "private_key_state": "unknown", "needs_renewal": false }
```

A certificate that cannot complete a TLS handshake, reported as needing
nothing. That is exactly the state a restored share-safe backup produces, since
those carry no key material by design.

After this release the same commands answer `"missing"` and `true`, and a key
that belongs to a different certificate is reported as `mismatched` rather than
believed. Backends that deliberately never fetch key material on the listing
path, such as Azure Key Vault, keep answering `unknown`: absence is not
evidence when nobody looked.

**Nothing to do after upgrading.** The state is computed on read, so the first
listing after the upgrade is already correct. If it now reports `missing` for a
certificate, that certificate could not serve TLS before this release either;
what changed is that you are told.

### A valid certificate was shown as expired

`days_left` is a whole number of days and rounds down, so a certificate with 23
hours of life left reports `0`. Eight places in the interface read "zero or
less" as expired, so such a certificate was given a red **Expired** badge,
counted in the Expired tile, matched by the Expired filter and labelled
"0 days ago".

This is not an edge case for anyone using a private CA: step-ca issues
24-hour certificates by default, so every certificate read as expired from the
moment it was issued.

`days_left` and `days_until_expiry` are unchanged, and still mean whole days.
Two new fields answer the questions they cannot: `expired` and `seconds_left`.
Both are `null` when the certificate could not be parsed at all, because
"unknown" is not "fine", and that conflation is what produced the original
misrendering. The interface now asks instead of deriving, sorts by seconds so a
certificate with hours left is not tied with one that lapsed an hour ago, and
says "less than a day left" where it used to say "0 days left".

**API contract 2.1 to 2.2.** A minor bump: two fields added, nothing removed or
retyped. Clients reading `days_until_expiry` keep working unchanged; clients
deciding validity from it should move to `expired`, because that calculation
cannot be made correct from a day count.

### Verification

The fix is checked against a certificate Let's Encrypt staging actually issued,
over Cloudflare DNS-01, into a container, read back through the API. The same
check against v2.32.1 fails with:

```
the instance just issued this certificate and holds its key, yet reports 'unknown'
```
